## 📋 设计原理

### 统一表结构
所有评委（书审、面试、决赛）都存储在 `user_accounts` 表中，通过以下字段区分：

```sql
-- 评委相关字段
role = 'REVIEWER'                    -- 评委角色（必须）
reviewer_group_code VARCHAR(32)      -- 书审分组码 (A1/B1/B2等)
interview_group_code VARCHAR(32)     -- 面试分组码 (A1/B1/B2等)
expert_background VARCHAR(32)        -- 专家背景 (MEDICAL/NURSING/MANAGEMENT)
```

### 三个评委池

1. **书审评委池** - 根据 `reviewer_group_code` 筛选
2. **面试评委池** - 根据 `interview_group_code` 筛选  
3. **决赛评委池** - 面试评委的子集或单独配置

## 🔧 后台API

### 获取评委列表

```http
GET /api/admin/reviewers
Authorization: Bearer {token}

查询参数:
  - institutionId: 机构ID (可选)
  - reviewerGroupCode: 书审分组码 (可选，如 A1/B1/B2)
  - interviewGroupCode: 面试分组码 (可选)
  - expertBackground: 专家背景 (可选，MEDICAL/NURSING/MANAGEMENT)
```

**示例:**
```bash
# 获取所有书审评委
GET /api/admin/reviewers

# 获取A1组的书审评委
GET /api/admin/reviewers?reviewerGroupCode=A1

# 获取医疗背景的评委
GET /api/admin/reviewers?expertBackground=MEDICAL
```

### 添加评委

```http
POST /api/admin/reviewers
Authorization: Bearer {token}
Content-Type: application/json

{
  "phone": "13900000001",
  "name": "王医生",
  "title": "主任医师",
  "institutionId": 1,
  "reviewerGroupCode": "A1",
  "interviewGroupCode": "A1",
  "expertBackground": "MEDICAL"
}
```

### 更新评委

```http
PUT /api/admin/reviewers/{id}
Authorization: Bearer {token}
Content-Type: application/json

{
  "name": "王医生",
  "title": "主任医师",
  "reviewerGroupCode": "B2",
  "expertBackground": "MEDICAL"
}
```

### 删除评委

```http
DELETE /api/admin/reviewers/{id}
Authorization: Bearer {token}
```

## 🎯 分配逻辑

### 自动分配 (ReviewService.autoAssign)

根据评审阶段 (`stage`) 选择对应的分组码：

```java
// 书审阶段 (BOOK) - 使用 reviewer_group_code
if (stage == ReviewStage.BOOK) {
    // 检查评委的 reviewer_group_code
}

// 面试阶段 (INTERVIEW) - 使用 interview_group_code  
if (stage == ReviewStage.INTERVIEW) {
    // 检查评委的 interview_group_code
}

// 决赛阶段 (FINAL) - 使用 reviewer_group_code
if (stage == ReviewStage.FINAL) {
    // 检查评委的 reviewer_group_code
}
```

### 分配规则

1. **机构回避**: 评委不能评审自己机构的项目
2. **重复检查**: 同一评委不能重复评审同一项目
3. **负荷限制**: 评委任务数不超过 `reviewerMaxLoad` (默认20)
4. **背景搭配**: 尽量保证同一项目的多个评委来自不同专家背景

## ⚠️ 注意事项

1. **没有专门的评委池表** - 评委信息都在 `user_accounts` 表中
2. **角色必须是 REVIEWER** - 不要把 CONTESTANT 等其他角色的用户分配评审任务
3. **分组码是字符串** - A1、B1、B2 等，不是数字
4. **三个池子共用一张表** - 通过不同的分组码字段区分
5. **前端显示的评委列表** - 就是数据库中 `role='REVIEWER'` 的所有用户
